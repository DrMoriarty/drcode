# Языко-агностичный код-индекс для drcode: design-документ

Статус: design (реализация не начата). Язык документа — русский; термины
инструментов и схемы остаются английскими (они станут именами в коде).

## 0. Сводка (TL;DR)

- **Экстрактор**: primary — tree-sitter (`py-tree-sitter-language-pack`,
  371 грамматика, встроенные `tags`-запросы), опциональный адаптер
  universal-ctags для языков вне пака. Гибрид, но не «ctags-ядро»: pip-зависимость
  переживает frozen-сборку PyInstaller, внешний бинарник ctags — нет.
- **Схема**: `.drcode/code_index.json` по образцу `search_index.json`:
  per-file записи, ключ `(mtime_ns, size)`, `"version"`, атомарная запись,
  повреждение → тихий rebuild. SQLite — отложенная альтернатива с критерием миграции.
- **Рёбра**: определения — точно (EXTRACTED); импорты — по таблице семейств
  языков (EXTRACTED, ~6 шаблонов); вызовы — эвристика «идентификатор в теле»
  (INFERRED), вычисляются на запрос, не хранятся. Честные метки в каждом ответе.
- **Инструменты**: `code_symbols`, `code_refs`, `code_callers`, `code_outline`
  для coding/tester/resolver ролей; без per-run gate (локальные дешёвые вызовы),
  с жёсткими капами вывода. Регистрация в `build_agent` по прецеденту web_fetch.
- **Включатель**: `code_index_mode: CodeIndexMode` (OFF/ON) в `ProjectSettings`,
  дефолт OFF; обязательная синхронизация трёх «зеркал учёта»
  (`pipeline_compaction.py:486`, `task_status_view.py:634`,
  `context_layout.py:223-231`).
- **Overlay** (идея semcode): правки агента в worktree накладываются stat-оверлеем
  поверх базового индекса; оверлей живёт в памяти процесса агента, гонок нет.
- **Фазы**: фаза 1 — индекс + `code_symbols` + `code_outline`; фаза 2 —
  `code_refs`, `code_callers`, overlay, ctags-адаптер.

## 1. Контекст и мотивация

В drcode нет никакого символьного/AST-анализа исходников (greenfield;
единственный `ast.parse` в `src/drcode/workflow.py:856` — сканер hook-функций).
Агенты читают код только «плоскими» инструментами: `read_file` /
`glob_files` / `grep_search` (`src/drcode/tools.py:295/376/407`). Чтобы найти
определение или вызывающих функции, агент читает файлы целиком — это десятки
тысяч токенов на каждый вопрос вида «кто вызывает X» и постоянный churn
compaction/eviction.

Цель — символьный индекс исходников + запросные инструменты для агентов,
**языко-агностичные**: без привязки к узкому списку языков программирования.
Результат — этот документ; реализация — отдельные задачи.

### 1.1 Уроки референсов

| Референс | Что взято | Что сознательно не берём |
|---|---|---|
| CodeRAG (JonnoC/CodeRAG) | идея per-language сканеров поверх общего графа | Neo4j и per-language сканеры как архитектурное ядро — это ровно та привязка к списку языков, от которой уходим |
| semcode (facebookexperimental) | overlay незакоммиченных правок (§7); честный call graph как *эталон*, а не как цель | libclang-точность: достижима только компиляторными средствами/LSP — вне скоупа (§11) |
| CodeGraphMCPServer | tree-sitter как extractor; метки достоверности рёбер EXTRACTED/INFERRED/AMBIGUOUS; NetworkX+SQLite как хранение | 16 per-language извлечателей (цена сопровождения); GraphRAG/комьюнити |

Предварительный вывод предварительного анализа («универсальность = ctags-скелет
+ эвристические рёбра») уточнён исследованием ниже (§2): универсальный скелет
доступен и через tree-sitter, а ctags остаётся опциональным расширением
покрытия, а не ядром.

## 2. Экстрактор символов (вопрос 1)

### 2.1 Кандидаты

**universal-ctags** (внешний бинарник, `--output-format=json`, чтение через
`readtags`):

- ✅ 300+ языков из коробки, десятилетия шлифовки per-language парсеров.
- ✅ JSON-вывод со scope/signature/kind — почти готовая схема.
- ❌ Внешний процесс. Для drcode это блокер уровня дистрибуции: приложение
  поставляется frozen-бандлами (onedir, `scripts/build-binary.sh`,
  `.github/workflows/build-binaries.yml` для macOS arm64 / Linux x86_64+arm64 /
  Windows). Пришлось бы собирать и тащить бинарник ctags на три платформы,
  без кросс-компиляции — отдельный CI-проект.
- ❌ Тел функций нет (только диапазон). Для `code_callers` (§5) тела нужны.
- ❌ Качество парсеров неравномерно; ошибки парсера молча дают дыры в индексе.

**py-tree-sitter-language-pack** (in-process):

- ✅ 371 язык одним pip-зависимым пакетом (README пакета; цитата: «Parse and
  understand source code in 371 languages … with one dependency and no
  grammars to compile»), парсеры скачиваются on-demand и кэшируются локально.
- ✅ Тела функций достаются по байтовым диапазонам узла — то, на чём стоит
  эвристика вызовов.
- ✅ Пакет бандлит стандартные `tags`-запросы (`.scm`) для заметной части
  грамматик — извлечение определений («function/class/method names»)
  без per-language кода. (⚠️ покрыты не все: в таблице грамматик встречается
  много `tags: ❌` — см. §2.3.)
- ❌ Маппинг «узел дерева → определение» per-грамматика, если писать руками.
- ❌ On-demand скачивание парсеров — проблема для frozen-сборки и offline
  (решение в §2.4).

### 2.2 Рекомендация: tree-sitter — ядро, ctags — опциональный адаптер

Экстрактор определяется интерфейсом, а не реализацией:

```python
class SymbolExtractor(Protocol):
    def languages(self) -> set[str]: ...
    def extract(self, path: Path, text: str) -> FileIndex: ...  # §4
```

- **Primary**: tree-sitter-адаптер. Извлечение определений — сначала
  скомпилированный `tags`-запрос грамматики (нуль per-language кода), при
  отсутствии — маленькая таблица node-kind'ов (§2.3).
- **Optional**: ctags-адаптер, включается автоматически, только если бинарник
  найден в PATH (`shutil.which("ctags")`) и язык не покрыт tree-sitter.
  Никогда не обязателен для работы фичи.

**Почему не «ctags-ядро»** (уточнение прежнего вывода): главный аргумент за
ctags был «сотни языков без per-language кода». Оказалось, что tree-sitter
закрывает тот же аргумент (bundled `tags`-запросы, 371 язык) и при этом
решает три проблемы ctags: in-process без внешнего бинарника (критично для
PyInstaller-бандлов), тела функций для эвристики вызовов, единая
структура ошибок. Аргумент «качество парсеров» остаётся за ctags — поэтому он
не выбрасывается, а становится адаптером расширения покрытия.

### 2.3 Реальная цена «только функции/классы/методы»

Скоуп извлечения намеренно узок: `function`, `method`, `class`, `interface`,
`struct`, `enum`, `trait`, `module` + сигнатурная строка. Это резко дешевле,
чем полный семантический анализ:

1. **Путь tags-запроса**: пакет даёт готовый `tags`-запрос — компиляция
   запроса + проход по capture'ам. ~30–60 строк кода *на весь пакт*, не
   на язык.
2. **Путь таблицы node-kind'ов**: для грамматик без `tags`-запроса — таблица
   `{имя языка: {kind_name: SymbolKind}}` (например
   `{"function_definition": FUNCTION, "class_definition": CLASS}` для Python).
   Оценка: 5–10 строк на язык; для «мейнстримной двадцатки» (py, ts/js, go,
   rust, java, c/c++, c#, ruby, php, swift, kotlin, …) — одна таблица
   ~100–150 строк. Всё остальное — имена узлов из одного дерева, они
   самодокументируются.
3. **Определение языка**: по расширению файла (маппинг из метаданных пакета);
   неоднозначные расширения (`.h`, `.ts` vs `.tsx`) — по содержимому/списку
   кандидатов, проигравший кандидат просто даёт пустой набор символов.
4. **Хвосты**: сломанный парсинг (`ERROR`-узлы на верхнем уровне) → файл
   индексируется частично, помечается `partial: true`; язык вне пака и без
   ctags → файл пропускается (индекс честно «не знает» такие файлы).

Итоговая оценка стоимости per-language сопровождения: **~ноль для покрытых
tags-запросами, ~5–10 строк для остальных мейнстримных**, что на порядок
дешевле «16 извлечателей» CodeGraphMCPServer.

### 2.4 Риск: on-demand скачивание парсеров в frozen-сборке

Пакет скачивает парсер при первом использовании. В frozen-бандле и/или offline
это недопустимо (run_bash в drcode и так не пускает внешний трафик; сам drcode
поставляется без сети на старте). Митигции (в порядке предпочтения):

1. `prefetch()` всех нужных грамматик при **сборке бандла** и включение
   кэша грамматик в payload `drcode.spec` (по аналогии с собиранием
   лениво-импортируемых `textual.widgets` — тот же класс ловушки).
2. Переменная окружения, указывающая на предзагруженный кэш грамматик.
3. Деградация: нет грамматики → инструменты честно отвечают «индекс недоступен
   для языка N, используйте grep_search».

Для dev-запуска (`uv run drcode`) скачивание разрешено — исключение
«бандл ≠ dev» уже существует для PortAudio.

## 3. Схема индекса (вопрос 2)

### 3.1 Формат хранения: JSON по образцу `search_index.json`

Решение: **`.drcode/code_index.json`** — тот же паттерн, что
`src/drcode/task_search.py` (индекс задач: `.drcode/search_index.json`).
Причины:

- Проверенный паттерн прямо в репозитории: per-file записи, ключ
  `(mtime_ns, size)` (`task_search.py:625-695`), версионированный JSON +
  атомарная запись `tmp` → `os.replace` (`_write_disk_index`, :598-608),
  `{}` при любом повреждении (:585-595), in-memory кэш под
  `threading.Lock` (:550-556). Переиспользуем всё, включая
  self-healing-семантику (тесты `test_index_reparses_only_changed_files`,
  `test_corrupted_index_is_rebuilt`, `test_stale_index_entry_self_heals`
  в `tests/test_task_search.py` — образцы для `tests/test_code_index.py`).
- `sqlite3` — stdlib и даст индексированный lookup по имени, но: (а) JSON
  достаточно быстр для целевых размеров (§3.4), (б) запись/валидация JSON
  проще и атомарна одной строкой, (в) миграция JSON→SQLite позже — это bump
  `version` + один адаптер загрузки, ничего из схемы не выбрасывается.

**Критерий миграции на SQLite** (фиксируем заранее): индекс > ~20 МБ на диске
или типовой `code_refs` > ~300 мс на проекте среднего размера. До порога — JSON.

### 3.2 Схема

```jsonc
// .drcode/code_index.json
{
  "version": 1,                       // bump при несовместимом изменении
  "generator": "drcode-<app-version>",
  "entries": {
    "<relpath>": [                    // ключ — путь относительно root (как у задач — filename)
      [<mtime_ns>, <size>],           // stat-ключ: не совпал → файл пере-парсится
      { "language": "python",
        "partial": false,             // true = ERROR-узлы, символы могли потеряться
        "symbols": [
          { "name": "_run_tool",
            "kind": "function",       // function|method|class|interface|struct|enum|trait|module|variable
            "scope": "drcode.tool_runtime",   // строка из ctags-совместимого scope, '' на верхнем уровне
            "signature": "def _run_tool(fn, *args, **kwargs) -> Any",  // первая строка определения, обрезана до 200 симв.
            "line": 12, "end_line": 48,   // 1-based, инклюзивно; тело = [line, end_line]
            "doc": ""                     // первые 2 строки docstring/комментария перед определением, ≤160 симв.
          }
        ],
        "imports": [                  // §5.2: семейство + сырой spec
          { "kind": "python", "spec": "drcode.tool_runtime" }
        ]
      }
    ]
  }
}
```

- Порядок символов — по `line`. Scope — плоская строка, конкатенация
  охватывающих имён (`"AgentDeps.build_agent"`), чтобы не изобретать дерево.
- Тела **не хранятся** — при запросах читаются с диска по `[line, end_line]`.
  Это держит индекс на порядки меньше исходников.
- `imports` хранится (дёшево, десятки записей на файл) и питает import-граф
  и ранжирование вызовов.

### 3.3 Поведение при повреждении и записи

Дословно контракт `task_search`:

- Любая ошибка чтения/парсинга индекса → `{}` → полная пере-индексация.
  **Никогда не фатально**; работа агентов не зависит от здоровья индекса.
- Запись: `tmp` + `os.replace` (атомарно на одной ФС), сбои записи глотаются —
  in-memory кэш обслуживает процесс, следующий write догоняет.
- Записи, не прошедшие валидацию формы (`_record_from_disk`-подобный фильтр),
  тихо пере-строятся.
- Один модуль-левел `threading.Lock` + кэш per project root; кросс-процессная
  безопасность — из атомарной записи и stat-ключей (потерянный апдейт файла
  индекса просто вызывает пере-парс).

### 3.4 Оценка размеров

Типовой проект 2 000 файлов × ~40 символов ≈ 80 тыс. символов ≈ 40 байт ×
~15 полей → **5–15 МБ JSON**, in-memory ~в 2–3 раза больше. Для целевого
случая drcode (репозитории на 10²–10³ файлов) — приемлемо; порог миграции в
§3.1. Файлы >1 МБ исходников — пропуск с пометкой (не наша аудитория).

## 4. Рёбра и достоверность (вопрос 3)

Модель меток — упрощение CodeGraphMCPServer до двух уровней (AMBIGUOUS не
вводим: у нас нет его источника неоднозначности — разрешённого по AST
разрешения имён; любая неоднозначность у нас уже есть INFERRED-шум).

### 4.1 Определения — EXTRACTED

Символ из индекса (tree-sitter узел или ctags-запись). Единственная «ложь» —
потерянные символы при частичном парсинге; лечится флагом `partial` и честным
выводом.

### 4.2 Импорт-граф по семействам языков — EXTRACTED (дёшево)

Полный per-language разбор импортов не нужен: на уровне «import-строки»
работает таблица **семейств** (~6 шаблонов, извлекаются тем же проходом
по строкам файла, без AST):

| Семейство | Шаблон (грубо) | Языки |
|---|---|---|
| python | `import X(.Y)` / `from X(.Y) import a, b` | py |
| es-family | `import … from 'X'` / `require('X')` | js/ts/jsx/tsx |
| go | `import "X"` (блок) | go |
| java-family | `import a.b.c;` / `package a.b;` | java, kotlin, c#, … |
| c-family | `#include "x.h"` / `#include <x>` | c, cpp, objc |
| rust | `use a::b::c;` / `mod x;` | rust |

Что это даёт без per-language кода: (а) файловый граф «кто кого импортирует»
для ранжирования вызовов (§4.3), (б) грубое разрешение имени
`X.foo` → файл(ы) модуля `X` в пределах проекта. Относительные пути (`./foo`,
`@/foo`, `from . import`) резолвятся тривиально; остальное — эвристика по
имени последнего сегмента (помечено как эвристика ранжирования, не факт).

### 4.3 Вызовы/ссылки — INFERRED (эвристика «идентификатор в теле»)

`code_callers(X)` работает так:

1. Собрать определения `X` из индекса (если несколько — все, с файлами).
2. Пройти по индексированным файлам, **начиная с импортирующих** модуль(и)
   определения (§4.2), и текстово искать `\bX\b` в телах функций
   (диапазоны из индекса; чтение с диска по запросу). Это «управляемый grep»:
   grep_search без индекса ищет по всем файлам, здесь — по заранее известным
   телам, с вырезанием комментарных зон не заморачиваемся (эвристика честная).
3. Хит в теле функции F → ребро «F вызывает X», метка **INFERRED**.
4. Фильтрация шума: определения `X` в самом теле F не считаются вызовом;
   совпадения в scope-префиксах (`X.foo()` и `bar.X()` различаются
   позиционно: ребро создаётся для `X.foo()` → `foo`, не для `X`).

**Оценка качества/ложных срабатываний** (честно):

- Уникальные имена (`_run_summarizer`) — точность близка к 100%: совпадение
  идентификатора в теле практически всегда и есть использование.
- Частые имена (`get`, `run`, `init`, `name`) — точность падает до десятков
  процентов: хиты чужих одноимённых символов, локальные переменные, слова в
  строках. Митигации, все дешёвые: ранжирование по import-близости;
  группировка ответа по файлу; в docstring инструмента — прямое
  «may include false positives for common names; verify by reading the line»;
  возврат строки-контекста (та строка файла, где совпало) — агент сам
  отбракует за один взгляд.
- **Ранжирование кандидатов — BM25-скоринг, не модель** (перенос результата
  задачи #0dc7fc65: на собственном коде drcode генеративные реранкеры дали
  ровно BM25-качество за 12 000–18 000 c CPU, а эмбеддинги — в пределах шума;
  «потолок задаёт пул кандидатов, а не ранжирующая модель»). Практически:
  вернуть ШИРОКИЙ пул хитов (аналог pool=200 из той задачи, +0.04 recall к
  узкому), отсортированный дешёвым лексическим скором — BM25 или простой
  tf-idf по «имени символа + строке контекста», in-process, без зависимостей.
  Никаких моделей в ранжировании — абляция уже показала, что они не добавляют
  ничего к лексическому матчингу на идентификаторах.
- Динамическая диспетчеризация (`getattr`, рефлексия, late binding) — не
  находится никоим инструментом этого класса; это цена отказа от LSP (§11).

Рёбра **не сохраняются в индекс** — вычисляются на запрос. Аргументы: (а)
индекс остаётся маленьким и «тупым» (только факты парсинга), (б) правила
эвристики можно менять без пере-индексации, (в) цена запроса мала
(текстовый поиск по заранее отобранным файлам). Если позже понадобится
хранение (кеширование тяжёлых запросов) — отдельный файл
`.drcode/code_edges.json` с той же схемой version/entries, без изменения
базового формата.

## 5. Запросные инструменты (вопрос 4)

Минимальный набор из четырёх инструментов. Все — **read-only**, блокирующие
тела через `tool_runtime._run_tool` (прецедент: `grep_search` в
`agent_build.py:677-688`), вывод капируется по символам (по образцу
`grep_search`: cap 100 строк, обрезка до 200 симв.).

Регистрация — в `build_agent`, паттерн web_fetch (`agent_build.py:1152-1183`):
`def` без декоратора + `__doc__ = f"""…"""` + `agent.tool(...)` (f-string
docstring обязан присваиваться, иначе pydantic-ai берёт пустое описание).

**Role-gating**: хелпер `code_index_tools_for(settings, role) -> bool`
(по образцу `web_fetch_policy_for` — единственный шов, который шарят
pipeline, compaction-учёт и context-layout; `web_fetch.py:267-281`).
Роли: **coding, tester, resolver, research** — да (research получает
инструменты на общих основаниях: его элементарные lookup'ы не должны
тратить слот `delegate_research` на вложенный запуск; сабагенты
наследуют решение родительского прогона);
subagent'ы `delegate_research` — **да, унаследованно** (они read-only
исследователи кода — главный выгодоприобретатель). Отсутствие настройки-вкл
→ None → инструменты не регистрируются (это само по себе переключатель).

**Бюджет**: **без per-run gate**. Обоснование: вызовы локальные, миллисекундные,
не создают внешнего трафика (в отличие от web_fetch, где gate защищает и
бюджет сети). Риск — раздувание контекста частыми вызовами; он закрывается
жёсткими капами вывода и уже существующими механизмами (`mark_unneeded`,
auto-eviction). Если наблюдения покажут злоупотребление — добавление простого
счётчика по образцу `SubagentGate` не меняет ни один из spec'ов ниже.

### 5.1 `code_symbols` — найти определение

```python
async def code_symbols(ctx: RunContext[AgentDeps], query: str,
                       kind: str = "", limit: int = 20) -> str
```

- **Что делает**: ищет определения по подстроке имени (case-insensitive),
  опциональный фильтр `kind` (`function|method|class|...`); скоуп — все
  индексированные файлы проекта.
- **Возвращает**: строки `path:line  kind  scope.name  signature` (+`doc`,
  если есть), в порядке (точное совпадение имени) → (префикс) → (подстрока),
  кратчайший путь первым. Ничего не нашлось → подсказка
  «index found nothing — fall back to grep_search» (§7.4).
- **Docstring** (проектный стиль web_fetch):

  > Find symbol DEFINITIONS in the project's code index (functions, methods,
  > classes, interfaces, …) by name substring — the cheap replacement for
  > reading whole files to locate a definition. `query` is a name substring
  > (case-insensitive); `kind` optionally filters (`function`, `method`,
  > `class`, …); `limit` caps results (default 20). Definitions are parsed
  > from source (EXTRACTED — reliable), but coverage depends on the language
  > being indexed; an empty result means "not indexed", not "does not exist"
  > — fall back to grep_search then.

### 5.2 `code_refs` — все вхождения идентификатора

```python
async def code_refs(ctx: RunContext[AgentDeps], name: str, limit: int = 50) -> str
```

- **Что делает**: все вхождения идентификатора `\bname\b` по индексированным
  файлам (текстовый поиск по файлам, отобранным индексом; тела не читаются —
  используется сама строка файла). Определения помечены.
- **Возвращает**: сгруппировано по файлу: `path:line: текст строки`;
  определения помечены `[def]`; сверху — счётчик «N files, M hits».
- **Docstring**:

  > List every occurrence of an identifier across indexed files — definitions
  > marked [def], the rest are usages (import sites, calls, plain mentions).
  > This is a TEXTUAL match: same-name locals, strings and comments appear
  > too — read the returned line, not just the location, before treating a
  > hit as a real usage. For "who calls this function" prefer code_callers.

### 5.3 `code_callers` — вызывающие (INFERRED)

```python
async def code_callers(ctx: RunContext[AgentDeps], name: str, limit: int = 30) -> str
```

- **Что делает**: эвристика §4.3: хиты `\bname\b` внутри тел функций
  (диапазоны из индекса), ранжирование по import-близости.
- **Возвращает**: `calling_function (file:line) → строка с совпадением`,
  отсортировано; каждая строка снабжена меткой. Ответ открывается
  служебной строкой: `callers are INFERRED from identifier matches — may
  include false positives (same-name symbols, strings); verify the line`.
- **Docstring**:

  > List functions that LIKELY call `name`, inferred from identifier matches
  > inside function bodies (NOT a compiler-accurate call graph). Ranked by
  > import proximity; may include false positives for common names — every
  > hit ships the matching source line so you can verify at a glance.
  > Dynamic dispatch (getattr, reflection) is invisible by design. Use
  > code_symbols to locate the definition, this to map its blast radius.

### 5.4 `code_outline` — структура файла/окрестность символа

```python
async def code_outline(ctx: RunContext[AgentDeps], path: str,
                       around: str = "", span: int = 0) -> str
```

- **Что делает**: (а) без `around` — скелет файла: все символы с их строками,
  kind и сигнатурами (то, что сегодня агент получает, читая файл целиком);
  (б) с `around: symbol-name` — окрестность: сам символ + соседи по уровню
  + при `span > 0` тело символа с диска (до `span` строк, кап ~400).
- **Docstring**:

  > Show a file's structure WITHOUT reading it whole: every definition with
  > its line, kind and signature (a map, not the code). With `around` — the
  > neighbourhood of one symbol (sibling definitions on the same nesting
  > level); `span` adds the symbol's actual body from disk, capped. Use this
  > to decide WHAT to read — then read_file the exact range.

## 6. Инкрементальность и staleness (вопрос 5)

### 6.1 Пере-парсинг по stat-ключам

Идентично `task_search`: каждый вызов индекса сначала stat'ит файлы (дёшево),
совпал `(mtime_ns, size)` — запись берётся из кэша/диска; не совпал — файл
пере-парсится, запись и диск обновляются. На типовом запуске агента
изменённых файлов единицы → цена «поддержания» индекса — миллисекунды.

### 6.2 Overlay правок агента (идея semcode)

Проблема, которую решает semcode: запросы должны видеть рабочую директорию
без пере-индексации. У нас она мягче — stat-ключи сами подхватывают правки,
но пере-парс на каждый запрос внутри одного хода агента — лишняя работа, а
для файла, который агент только что отредактировал, — ещё и риск частичного
парсинга прямо под ним.

Решение — **двухслойная запись**:

- **Базовый слой**: персистентный индекс (§3), всегда про закоммиченное
  состояние рабочей директории.
- **Оверлей**: in-memory, per-process: файлы, чей текущий `(mtime_ns, size)`
  отличается от индексного, парсятся при первом обращении и держатся в
  оверлее до конца процесса (или до следующего stat-несовпадения). Запросы
  читают оверлей поверх базы. Это stat-оверлей в духе semcode, но без
  git-механики: мы не строим diff с HEAD — мы просто признаём, что «текущее
  содержимое файла» == истина, а индекс — кэш о нём.

Трекинг правок (`_track_edited_file` в `agent_tools.py`) может дёшево
подсказывать оверлею, какие файлы виноваты, но не обязателен: stat-сравнение
самодостаточно.

### 6.3 Откат к живому grep, когда индекс молчит

Принцип: индекс — ускоритель, а не источник истины. Каждый инструмент при
пустом результате возвращает хвост-подсказку «not indexed here — use
grep_search/read_file» (в docstring'ах выше). Дополнительно: файл без языка
(вне пака/ctags) просто не участвует в индексных ответах — grep_search его
по-прежнему видит, так что агент не теряет покрытие, только скорость.

### 6.4 Смена ветки в главном чекауте

`git checkout` переписывает файлы → у них меняются `mtime_ns`/`size` →
stat-ключи инвалидируются сами. Остаточные риски:

- Файл, заменённый в ветке на контент того же размера с тем же mtime (секундное
  окно, git обычно трогает mtime) — практическая редкость; страховка —
  self-healing: любая запросная аномалия (запрошенный диапазон за пределами
  файла) инвалидирует конкретную запись (прецедент
  `test_stale_index_entry_self_heals`).
- Дешёвая добавка (фаза 2): хранить в индексе `git rev-parse HEAD` главного
  чекаута; не совпал при загрузке → оверлей сбрасывается, база валидируется
  выборочным хэшем первых K файлов. Оптимизация, не корректность.

## 7. Worktree-изоляция и параллелизм (вопрос 6)

### 7.1 Путь индекса — по главному чекауту

Индекс физически один: `<manager.storage.root>/.drcode/code_index.json`.
У worktrees своего `.drcode/` нет — `.drcode` в `_COPY_SKIP_DIRS`
(`task_env/_common.py:48-67`), так что копировать/создавать ничего не надо.
**Прецедент резолва — `search_task_history` в `agent_build.py:996-1007`**:
путь берётся из `manager.storage.root`, не из `ctx.deps.root`
(в изолированной задаче `deps.root` — это worktree). Новый инструментарий
обязан следовать ровно этому правилу, иначе два слота создадут себе
индивидуальные индексы и получат рассинхрон.

### 7.2 Параллельные слоты в одном процессе

Тела инструментов идут через `tool_runtime._run_tool` (worker-потоки).
Общий доступ — модуль-левел `threading.Lock` + кэш per root (дословно паттерн
`_ARCHIVE_LOCK` / `_ARCHIVE_CACHES`, `task_search.py:550-556`). Fast-path
(stat-обход) — вне лока, как в `load_archive` (:671-682).

### 7.3 Конфликт двух worktree-агентов

Ключевое следствие дизайна: **базовый индекс worktree-агенты только читают**;
их правки живут в **собственном in-memory оверлее процесса** (§6.2). Записи
в общий файл идут только при пере-парсе общего базового слоя — и они
атомарны (`os.replace`) и консистентны (stat-ключи), так что «проигравший»
писатель просто заставляет следующего читателя пере-парсить. Сценарий гонки
максимум стоит миллисекунды, никакого логического конфликта нет. Это
осознанное отличие от гипотезы «per-worktree overlay-файлов», которая
породила бы настоящую проблему (два агента пишут один overlay-файл);
in-memory оверлей её снимает структурно.

Межпроцессный случай (drcode + drcode-bench или desktop-табы, процессы
раздельные) — тот же ответ, что у `search_index.json`: атомарная запись +
stat-ключи, потерянный апдейт = пере-парс.

## 8. Настройка-включатель (вопрос 7)

### 8.1 Поле

```python
class CodeIndexMode(StrEnum):
    OFF = "off"   # инструменты не регистрируются, индекс не строится
    ON  = "on"    # индекс + инструменты для coding/tester/resolver/research/сабагентов

class ProjectSettings(...):
    code_index_mode: CodeIndexMode = CodeIndexMode.OFF
```

- Образцы: `web_fetch_mode` (`settings.py:574-585`, enum с `label`-методом,
  `WEB_FETCH_MODE_OPTIONS` :239-243) и `auto_context_unloading`
  (:634-649, «opt-in per project, читается при активации»). Дефолт **OFF** —
  консистентно с обоими соседями: фича новая, цена первого включения
  (полная пере-индексация) должна быть осознанной.
- Пикер: «Task settings…» palette — опция с `CodeIndexMode` + label-метод
  («one-line explanation shown in the Settings palette»); применяется со
  следующей активации (чтение при активации — уже существующее правило).
- `task_settings_hints` (`settings.py:911-1040`): хинт, когда режим ON, но
  ни один язык проекта не покрыт (индекс пустой при непустом src) —
  «index built, but 0 files matched; check extractor availability».
- Только ON/OFF: промежуточные режимы (типа allowlist языков) — YAGNI;
  enum оставляет место для роста без смены поля.

### 8.2 Три зеркала учёта (обязательные)

Схемы инструментов попадают в оценку заполнения контекста через
`coding_tool_schemas`; все три вызывающих места обязаны передать
`code_index_mode` (точнее, его действующее значение для роли), иначе
оценка «misses (or invents) the schemas» — прямая цитата докстринга
`context_layout.py:218-233`:

1. `core/pipeline_compaction.py:486` — гейты compaction.
2. `tui/task_status_view.py:634` — отчёт TUI.
3. `src/drcode/context_layout.py:223-231` — отчёт context-layout.

Это тот же «three accounting mirrors»-шов, через который прошли web_fetch и
subagent'ы; пропуск любого из трёх = рассинхрон счётчиков, который всплывает
как непредсказуемая разница между показанным и реальным fill.

### 8.3 Запуск и пере-индексация

- **Лениво при первом запросе** (рекомендация): первый вызов любого
  code_* инструмента в процессе строит индекс (в worker-потоке уже и так —
  `_run_tool`). Один service-ивент при первом построении
  («code index: N files, M symbols, K languages, T ms» — visibility в чат,
  не в модель). Нет фонового воркера, нет CLI — минимальная поверхность.
- Полная пере-индексация = удалить `.drcode/code_index.json` (или операционный
  хук `clear_code_index_cache()` по образцу `clear_archive_cache`,
  `task_search.py:611-622`) — индекс восстановится лениво.
- Фоновая пере-индексация (watcher) и CLI-флаг — сознательно отложены:
  stat-ключи делают «поддержку» бесплатной, а постоянный воркер противоречит
  ресурсной дисциплине проекта (агенты и так живут в перегруженных слотах).

## 9. Экономика контекста (вопрос 8)

### 9.1 Оценка выигрыша

Сценарий «кто вызывает X» сегодня: агент делает grep_search (10-50 строк
попаданий без контекста определения) → читает 3–8 файлов-кандидатов по
200–2000 строк. Стоимость: ~10 000–50 000 токенов чтения + мусор в контексте,
который потом вычищается eviction'ом.

С индексом: `code_symbols(X)` (≤20 строк ≈ 200 токенов) → `code_callers(X)`
(30 хитов с контекстными строками ≈ 500–1 500 токенов) → чтение точечных
диапазонов через `code_outline(around=X, span=N)` вместо целых файлов.
**Выигрыш ~10–50×** на этот класс вопросов; для «найти определение» — до
~100× (200 токенов против чтения файла на 2–5k токенов вслепую).

Второй, менее видимый эффект: меньше «слепых» read_file → меньше
промежуточных результатов, которые приходится помечать `mark_unneeded`
и очищать auto-eviction'ом → меньше инвалидаций prompt-cache.

### 9.2 Интеграция (кратко, по условию)

- **Eviction/compaction**: результаты code_* — обычные tool-returns, ничего
  специального не требуется; они автоматически подпадают под `mark_unneeded`
  и auto-eviction. Единственная обязанность — зеркала (§8.2), чтобы размер
  схем был в учёте.
- **delegate_research-брифы**: в секции «Read-only subagents» системного
  промпта и в docstring'ах инструментов добавить одну строку-триггер
  («map call sites / survey a subsystem» уже есть триггер-список —
  дополнить упоминанием, что code_symbols/code_callers — правильные
  стартовые точки брифа). Без глубокой проработки.

## 10. Не-скоуп (вопрос 9)

Фиксируем явно, чтобы не превратить индекс в проект-пожиратель:

| Исключено | Почему | Что вернуть позже |
|---|---|---|
| Embedding/семантический поиск | **измерено на собственном коде** (задача #0dc7fc65, golden-датасет 917 задач, test=100 запросов): BM25 = 0.294 r10_strong за 0.6 c; эмбеддинги 0.284–0.308 — в пределах шума (±0.01); плюс модель/векторная БД, другой класс отказов | если появится необходимость «найти по смыслу» — брать класс «эмбеддинги» (в ~35–50 раз дешевле реранкера при равном качестве), НЕ генеративные реранкеры |
| Генеративные реранкеры результатов поиска | закрыты навсегда, абляция #0dc7fc65: реранкеры (Qwen3-0.6B/1.7B, Gemma-3-1B) дали ровно BM25-качество (0.294 = 0.294) за 12 431–18 429 c wall на CPU; dev-эффект +0.017 не подтвердился на test (шум) | нет |
| GraphRAG / комьюнити-детекция | из CodeGraphMCPServer; дорого и не нужно для ответов «кто/где» | не планируется без пользовательского запроса |
| LSP-оркестрация | per-language серверы = ровно та привязка к списку языков, от которой уходим; тяжёлые процессы | возможно, точечно, когда появится роль, живущая в одном языке |
| Точный call graph (semcode/libclang) | только компиляторными средствами; INFERRED-эвристика покрывает потребность агентов с честной меткой | пере-открыть вопрос, если ложные срабатывания станут измеримой болью |
| MCP-клиент к внешним индексам (semcode, CodeGraphMCPServer) | у агентов drcode нет MCP-клиента; подключение внешнего процесса = новая поверхность отказов | наш индекс можно выставить *наружу* через `mcp/tools.py` READ_TOOLS (фаза 3, опционально) |
| Хранение рёбер вызовов в индексе | см. §4.3 | отдельный файл, если кеширование станет нужным |
