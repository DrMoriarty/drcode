# Этап 2: детерминированный harness кандидатов (fastcontext-scout)

**Вопрос этапа**: сколько даёт ОДИН детерминированный harness (без модели) на
задаче «запрос → релевантные файлы», и какой интерфейс оставить этапу 3 для
подключения реранкеров.

## Что построено

- `scripts/candidates.py` — общий интерфейс кандидатов:
  `query (str) -> [{path, start_line, end_line, score, source}]`, сортировка по
  убыванию score. Чанкинг по функциям/классам: одна верхнеуровневая сущность =
  один чанк + «шапка модуля» (docstring/импорты) + методы больших классов (>120
  строк); каждый чанк с заголовком `path:start-end, сигнатура`.
  **Отклонение от плана**: tree-sitter недоступен (нет сети, нет в кэше uv) —
  чанкер написан на stdlib `ast` (индекс только python, для src/drcode этого
  достаточно). Точка замены изолирована — `chunk_file()` в `candidates.py`.
- Бейслайны (режимы для абляций), все за одним интерфейсом:
  - `rg` — ripgrep-ключи: примитивное извлечение ключевых слов из запроса
    (пути/идентификаторы — сильный вес, обычные ascii-слова — средний,
    кириллица — слабый 0.4; для идентификаторов генерируются варианты
    snake_case/camelCase/kebab), матчинг литералами (`rg -F`), счёт по чанкам;
  - `bm25` — Okapi BM25 по чанкам (своя реализация, k1=1.2, b=0.75; rank_bm25
    недоступен offline; в документ чанка добавлены токены пути, имя файла ×2);
  - `rg+bm25` — reciprocal rank fusion (k=60) на файловом уровне;
  - `bm25+struct` / `rg+bm25+struct` — структурный буст: соседи по графу
    импортов (ast-парсинг `import`/`from … import`, разрешение относительных
    импортов и from-импортов подмодулей) от топ-8 файлов внутреннего
    ранжирования; импортируемый файл получает 0.5×score источника,
    импортирующий — 0.3×; для `from mod import sym` кандидатом становится чанк
    с именем `sym`, иначе шапка модуля.
- `scripts/evaluate.py` — метрики против датасета этапа 1, файловый уровень
  (релевантность — файлы, кандидат — чанк, файл засчитывается по первому
  вхождению): recall@k (5/10/20), recall@budget — жадная упаковка чанков по
  убыванию score в пакет ≤ B токенов, B ∈ {2k, 4k, 8k}, токены = chars/4 по
  выданным чанкам (заголовок + тело; чанки уже покрытых файлов пропускаются),
  MRR. Отдельно по label=strong и по всем релевантным (strong+weak).

Индекс: `src/drcode`, 138 файлов, 1547 чанков, медианный чанк 23 строки,
~1.0M «токенов» (chars/4). Всё локально, без сети.

## Два потолка recall (важно для чтения таблиц)

Датасет размечен по историческим задачам, а индекс — по **текущему** коду:

1. **tests вне индекса.** По ТЗ индексируется только `src/drcode`, а в
   релевантных регулярно фигурируют `tests/*.py` — они недостижимы в принципе.
2. **Протухшие пути.** Часть релевантных файлов с тех пор переименована/разъехалась
   (`drcode/voice.py` → пакет `voice/`, `tui/actions.py` → `actions_forms.py` +
   `actions_lifecycle.py`, `tui/pipeline.py` → `core/`…): доля несуществующих
   путей — **dev: 38.6% всех / 43.5% strong; test: 37.9% / 44.9%**;
   mean share of relevant files inside the index (потолок recall по всем
   релевантным): **dev 50.4%, test 60.2%**.

Поэтому кроме основной таблицы (знаменатель — все релевантные, попавшие в
топ-файлы — только достижимые) считаем **live-подвыборку**: задачи, у которых
хотя бы один strong-файл существует в текущем индексе (dev 26/40, test 542/832).
Именно live-числа — честная точка отсчёта этапа 3.

## Выводы

1. **BM25 — единственный канал, который нужен детерминированной части.** Он
   стабильно лучший одиночный бейслайн на всех метриках и обеих выборках
   (live strong r@10: 50.1% dev / 41.8% test; MRR: 88.9% / 56.9%). Статический
   индекс строится один раз, запрос стоит миллисекунды (832 запроса — 10.6 с;
   rg-режимы — ~200 с из-за subprocess).
2. **Структурный буст в текущей форме почти нейтрален** (±0.2 п.п. на bm25).
   Причина: он добавляет соседей ПОД топ внутренних результатов (0.5×score),
   а у bm25 плотное распределение — соседи редко влезают в топ-10/20; там, где
   влезают, это в основном уже покрытые диалоги/сиблинги. На rrf-варианте буст
   чуть помогает на больших k (test r@20: 37.0→38.9, live 47.9→49.3), но убивает
   бюджетные метрики (rb@4000_strong: 22.5→23.0 чуть лучше, но rb@2000 16.1→16.4
   — в пределах шума; главная потеря — rrf сам по себе хуже bm25). Для этапа 3
   struct стоит оставить как ОТДЕЛЬНЫЙ канал/фичу реранкера («соседи по импортам
   от seed-файлов»), а не как пост-буст к лексике.
3. **rg-канал слабее bm25 везде** (live strong r@10: 27–32% против 42–50%), и
   RRF с ним не улучшает bm25: у rg много ложных срабатываний на частых
   идентификаторах (`drcode`, `settings`, `pipeline`). Как самостоятельный
   канал rg не нужен; как генератор ключей для фич реранкера (есть ли термин в
   пути/чанке) — возможно.
4. **Где хватает комбинации**: уже `bm25` одному хватает на типовом feature/bug
   запросе с упомянутыми файлами/идентификаторами — MRR 89% на dev-live значит,
   что первый релевантный файл почти всегда в первой же паре чанков. Пакет 4k
   токенов покрывает ~34% (test-live) / 43% (dev-live) strong-файлов — это и есть
   база, с которой этап 3 сравнивает реранкеры.
5. **Где лексика проваливается** — см. разборы ниже: чисто-русские описания UI-
   симптомов без идентификаторов (нулевой лексический сигнал), короткие запросы
   с одним неявным идентификатором, протухшие пути датасета.

## Разборы ошибок (режим bm25+struct)

### 1. dev `247eeaa3` — чисто русский запрос, нулевой лексический сигнал

- **Запрос**: «Проблема в обновлении левого сайдбара. Когда задача ушла в
  активные… группа Актив в скобочках два. Нарушение порядка отображения
  пунктов списка».
- **Что искали**: `tui/chat_view.py` (strong), `tests/test_sidebar_reconcile.py`
  (strong, вне индекса), `tui/sidebar.py` (weak).
- **Что нашлось**: пусто — bm25 не имеет ни одного токена запроса после
  отбрасывания кириллицы (все паттерны rg — русские слова весом 0.4).
- **Диагноз**: единственный канал сигнала здесь — семантика («сайдбар» →
  sidebar). Лексический harness принципиально не решает такие запросы; это
  главная ниша реранкера/эмбеддингов этапа 3.

### 2. test `04ce0a6b` — короткий запрос, идентификатор введён неявно

- **Запрос**: «В drcode-models кнопка Delete не влезает по ширине и обрезается».
- **Что искали**: `tui/model_setup_app.py` (strong).
- **Что нашлось**: ранги 11–20 (r@20 strong = 1.0, r@10 = 0.0); топ забит
  `merge_engine.py`, `settings.py`, `conflict.py` — общие токены `models`,
  `settings`, `delete` тянут всё подряд; kebab-токенизация `drcode-models`
  дала `drcode`+`models`, что матчилось в `drcode/models.py`.
- **Диагноз**: нужный файл существует и лексически достижим, но не хватает
  знания «drcode-models — это экран ModelSetupApp». Реранкер с знанием имён
  экранов (или историю прошлых задач) вытащил бы; из дешёвого — буст файлов по
  совпадению полного имени экрана.

### 3. test `8b7620f9` (и dev `51f2efc8`) — ложный промах: пути протухли

- **Запрос**: SIGSEGV при голосовом вводе (push-to-talk, Ctrl+B, PortAudio…).
- **Что искали**: `tui/voice_input.py`, `drcode/voice.py` (strong) — оба пути
  в текущем коде не существуют (разъехались в `voice/`-пакет и `core/`).
- **Что нашлось**: `voice/__init__.py`, `voice/_sounddevice.py`,
  `voice/recorder.py`, `voice/playback.py`, `core/voice_input.py` — то есть
  по существу **правильное место**: harness нашёл новые модули того же кода.
- **Диагноз**: recall «0.0» здесь — артефакт протухшей разметки, а не слабости
  harness'а. Для честной оценки этапу 3 нужно либо рематчить релевантные пути
  на текущее дерево (по имени/символам), либо мериться только на live-подвыборке.

### 4. test `22a0ed7b` — запрос с точными адресами, но файлы разъехались

- **Запрос** (en): подробно описывает кейс с `.viewed`/`$panel`, со ссылками
  `app.py:194`, `actions.py:205`, `actions.py:416`.
- **Что искали**: `tui/actions.py`, `tui/chat_view.py`, `tui/state.py` (strong)
  + `tests/test_sidebar_reconcile.py`; из них в индексе нет ни одного:
  `actions.py` разъехался на `actions_forms.py`/`actions_lifecycle.py`.
- **Что нашлось**: `tui/actions_forms.py` (осколок того же кода!),
  `tui/sidebar_view.py`, `tui/app.py`, `tui/chat_timeline.py`.
- **Диагноз**: как и №3 — переименование съело метрику (при этом harness
  фактически нашёл преемников). Дополнительно видно: путь-токены `actions`,
  `app` слишком частотны, чтобы быть дискриминативными — веса для
  «путь:строка»-ссылок стоит поднимать только для существующих файлов.

### 5. test `be37b43e` / `b4cc5400` — релевантный файл вне индекса по построению

- **Запрос**: flaky-тест `tests/test_resolver_retry.py::…` / падение
  `tests/test_network_app.py::…` с детальным выводом pytest.
- **Что искали**: сам тестовый файл (strong) + `tests/network_mocks.py` (weak).
- **Что нашлось**: код под тестом — `core/pipeline_resolver.py`,
  `merge_resolver.py`, `agent_build.py`, `core/pipeline_agent_run.py` — по
  существу релевантный контекст, но сам тест недостижим.
- **Диагноз**: queries про падающие тесты — регулярный класс (в датасете их
  заметная доля); индекс без `tests/` гарантированно теряет их. Для этапа 3
  дешёвое расширение — индексировать `tests/` тем же чанкером (или держать
  тесты как файловый уровень без чанков).

## Что оставить этапу 3

- Интерфейс `providers.search(query) -> [{path, start_line, end_line, score,
  source}]` + `index.chunk_of(cand)` для токенов/текста — реранкер получает
  кандидатов с заголовками и телом, не зная, какой бейслайн их породил
  (поле `source` сохранено для фич).
- Канал по умолчанию — `bm25`; `struct` — отдельным каналом от seed-файлов;
  `rg`-ключи — только как признаки.
- Метрики и «живая» подвыборка зафиксированы в `scripts/evaluate.py`
  (`--errors` даёт дамп худших записей для глазной проверки реранкера).
