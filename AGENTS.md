# AGENTS.md

## Commands

```bash
uv sync                                    # install deps into .venv (Python 3.12, src layout)
uv run drcode                              # run the TUI — operates on the CURRENT directory (Path.cwd())
uv run pytest                              # whole suite (testpaths=tests, asyncio_mode=auto)
uv run pytest tests/test_task_manager.py -k hold   # focused run
uv run ruff check src                      # lint (no config; ruff defaults)
uv run ruff format src
uv run pyright                             # typecheck (dev dep; no config)
```

No CI or pre-commit hooks exist — verify changes with ruff + pyright + pytest, and exercise the TUI by launching `uv run drcode` in a scratch directory.

## Version & packaging

- The bare `version` file at the repo root is the single source of truth for the app version (hatchling reads it via a custom pattern; `src/drcode/version.py` exposes `APP_VERSION`). Bump it there — never in `pyproject.toml` (`version` is dynamic).
- System/compaction/init prompts are package data in `src/drcode/prompts/`, read as text at import time (`prompts.py`) and shipped in the wheel via the pyproject `include`.
- Standalone binary: `bash scripts/build-binary.sh` (provisions PyInstaller via `uv sync --group build`; platform-specific, no cross-compilation). Onedir on purpose — see README for why; `DRCODE_ONEFILE=1` builds the legacy single-file. `drcode_entry.py` is the PyInstaller stub; it sets `PYDANTIC_DISABLE_PLUGINS=logfire-plugin,logfire` because the logfire pydantic plugin crashes in a frozen app.
- Headless CLI (entry point `drcode:main`): `drcode --bug-report DESC` / `--feature-request DESC` create a task without the TUI; `--git-hub-sync` runs one GitHub Issues sync cycle.
- Releases are tag-driven: pushing a `v*` tag runs `.github/workflows/build-binaries.yml`, which builds the onedir bundle per platform (macOS arm64, Linux x86_64/arm64, Windows) and attaches archives to a GitHub Release. No CI runs tests — local `ruff` + `pyright` + `pytest` is the only gate.

## Configuration gotcha

The agent needs `model` and `base_url`; `api_key` is optional (keyless local gateways work). Settings are layered (higher wins): `DRCODE_*` env vars > project `.env` / project `.drcode/drcode.json` > user-level `~/.config/drcode/drcode.json` (XDG_CONFIG_HOME-aware) > built-in defaults (see `src/drcode/config.py`; a corrupted json file is skipped, never fatal). On first start the user config dir is scaffolded with `drcode.json.example` built from the `Config` fields — when adding a new user-configurable field without a sensible default, add a placeholder to `_EXAMPLE_PLACEHOLDERS` in `config.py`. When nothing anywhere provides model/base_url, the TUI opens a modal setup dialog on startup: model and URL are required, ESC skips (app runs without a model — tasks still work, pipeline stays idle); Save probes the endpoint live and persists the values into `<project>/.drcode/drcode.json` (`Config.save_to_project`, merged with existing keys). `base_url` defaults to the OpenAI API; any OpenAI-compatible endpoint works.

Project-scoped user preferences (retention, task finalization, stall nudge, GitHub sync, ntfy notifications) live separately in `<project>/.drcode/settings.json` (`src/drcode/settings.py`, `ProjectSettings`) — deliberately NOT part of `Config`, which is env-driven model/API settings.

Multiple providers/models per role: the user-level catalog `~/.config/drcode/models.json` (`src/drcode/providers.py`, `UserModelsConfig` — providers with base_url/api_key/health_check_url and their models, plus per-role defaults) is written ONLY by the `drcode-models` utility or the main TUI's "Provider catalog…" screen (same `ModelCatalogScreen`); models are auto-discovered via `agent_model.fetch_models`. Each `ModelEntry` carries the model's token caps — `max_context_tokens`, optional `max_tokens` and an optional per-model `compaction_threshold` (null = inherit the flat config's value) — so the model–context–compaction-limit triple is one unit: assigning the model to an agent role brings all three with it. The project picks a model per agent role under the optional `models` key of `.drcode/drcode.json` (values `"provider/model-id"`, null/absent = user default). Effective per-role connection: `providers.resolve(config, role)` — precedence `DRCODE_MODEL`/`DRCODE_BASE_URL` env (all roles) > project `models[role]` > catalog default > flat config; the pipeline passes the resolved copy to `build_agent`/`build_tester_agent`/`build_compaction_agent`, and the header probe/context-fill math uses the resolved CODING model. Compaction gates (`pipeline._fill_over_threshold`) always take a role and use that role's resolved config — both the context size and the threshold — so the tester round is measured against the tester model's window and limit, not the coding model's.

## Architecture

Task-centric coding agent (pydantic-ai + textual), inspired by opencode. Single package under `src/drcode/`:

- `task_manager.py` — state machine: queued → active → testing → completed, plus awaiting-clarification: the agent's `ask_clarifying_question` tool pauses the task on a question and the pipeline advances; when the user answers, the task re-enters the pipeline at the head of the queue (activated once no testing is pending and nothing is active — promotion is up to the app). At most one ACTIVE task; when it's marked done (development finished) it moves to TESTING — only the tester moves it to COMPLETED via its `set_verification` tool (which stamps the passed/failed label). A task also auto-completes (goes to TESTING) when the agent finishes its run with no pending input, no clarification and no unfinished attempt; aborts and agent errors keep the task paused via `task.unfinished` instead. Sending input to a COMPLETED/TESTING task re-queues it (the old verification label is cleared). On startup any stale ACTIVE task is demoted to queued, and all tasks stuck in TESTING are re-tested FIRST, before any queued task is taken into development (awaiting-clarification tasks survive restarts). `promote_next` activates a queued task that has pending input OR an unfinished attempt (auto-resume of interrupted work) — never a held one: the user can park a queued task out of the backlog (`set_hold`, Ctrl+H); a held task keeps its pending input and queue stamp but is skipped until resumed — or deleted (`delete`, Ctrl+Delete; only held tasks can be deleted). `cancel` (Ctrl+X) drops all pending input and completes the task immediately — the tester is skipped everywhere a finished task would run it. `research` tasks never go to TESTING: `mark_done` completes them right away. The kind of a still-queued task can be changed (`set_kind`, Ctrl+T): bug re-positions it at the head of the queue, feature — at the tail. Manual reordering (`move_in_queue`, Ctrl+Up/Down): one step up = away from execution, one step down = closer to it; the order is re-stamped into `queue_seq` so it survives restarts, and moves never cross the bug block. Queue order is `(bugs newest-first, queue_head, queue_seq)` — tester-created bug reports land at the very head.
- `models.py` — `Task` holds the full pydantic-ai transcript as serialized `ModelMessage` dicts (`task.messages`); queued user input lives in `task.pending_input` until the agent run consumes it. `task.unfinished` marks an interrupted attempt (abort/agent error): the consumed prompt is NEVER re-queued — it stays in the transcript at its chronological position, and the next activation resumes the attempt without re-sending text. Tester runs are persisted separately in `task.tester_messages` (one serialized transcript per testing round) so they never leak into the coding agent's model history; the chat renders each round behind a "testing" separator. `task.events` (`TaskEvent`: timestamp + text) is the service-event log — shown in the chat under a "service events" separator, but never fed to the model. Tasks imported from GitHub issues carry the issue number in `task.github_issue` (the tester appends "Fixes #N" to its commit message).
- `storage.py` — persists each task as `<project>/.drcode/tasks/<id>.json` (atomic tmp-file write; corrupted files are moved to `.json.bak`, not deleted). `.drcode/` is gitignored (enforced by `gitignore.py`).
- `agent.py` — thin orchestrator only: wires the coding/tester/compaction agents to their tools and deps. It re-exports the split-out modules' names so the TUI and tests keep importing everything from `drcode.agent`:
  - `agent_model.py` — model/network layer: builds the `OpenAIChatModel`, `probe_model` availability check, `fetch_models` auto-discovery (context size probed from optional gateway keys, else 200k default + "needs confirmation" flag), `EXTRA_HEADERS`.
  - `tool_runtime.py` — runs blocking tools in a worker thread (a stall would freeze the Textual UI); fixable errors (`ValueError`/`OSError`/`re.error`/`PathViolation`) are converted to `ModelRetry`, everything else would crash the run. `PathViolation` is additionally logged into the task's service-event history.
  - `transcript.py` — `serialize_messages`/`load_messages` round-trip transcripts; `resumable_history` trims an incomplete tail (unanswered tool calls / bare tool results); `sanitized_messages` applies the same trim at interrupt time so the stored transcript stays API-valid no matter in which order later messages are appended; `ends_with_open_request`, usage/context-token accounting, `extract_display` for the chat UI.
  - `compaction.py` — when context fill reaches `Config.compaction_threshold`, a tool-less summarizer rewrites the transcript into an anchored summary (`compaction.txt`/`compaction.md` templates); original user prompts stay verbatim, the summary rides in a synthetic message prefixed `COMPACTION_SUMMARY_PREFIX` (fed back on the next compaction, rendered as "context compacted" in chat).
- `tools.py` — filesystem/shell tools. Reading works anywhere on the filesystem; writing is jailed to the project root and `/tmp` (symlink-aware, so `/private/tmp` on macOS counts too) — violations raise `PathViolation`. `run_bash` inspects the command first and refuses `rm`/`mv`/`cp` whose path arguments escape the writable area. Grep/glob skip `IGNORED_DIRS` (add new cache dirs there).
- `github.py` — GitHub Issues sync (project settings `github_*`): open issues labeled `bug`/`enhancement` become local tasks; `invalid`/`wontfix` and unlabeled issues are dismissed (recorded as seen, never reconsidered).
- `tui/` — `app.py` is the textual app; the agent/pipeline logic lives in `pipeline.py` as a mixin (`run_agent`, the `_advance()` gate), with the interface in `state.py`. `run_agent` is a `@work(exclusive=True, group="agent")` worker whose loop processes messages strictly chronologically: pending input in arrival order, then at most one continuation turn (`agent.iter(None, …)`) when `task.unfinished` and the transcript ends with an unanswered request; the interrupted prompt is never re-queued, and both the cancel and error handlers sanitize the transcript instead of re-queueing text. Agent errors push the failed attempt to `unfinished` + demote the task to QUEUED so nothing is lost. Pipeline advancement goes through the single `_advance()` gate: while any task is TESTING, no new development ever starts — the oldest TESTING task is (re)tested first, and a failed tester run is retried with capped exponential backoff (the retry timer re-advances). A stall watchdog (project setting) aborts and restarts a run showing no life; the same nudge is manual (Ctrl+R). Cancelled workers (abort, superseded runs) do not restart the pipeline. Service events are persisted via `_log_event`/`_show_event` regardless of which task is open in the chat.

## Testing quirks

`tests/conftest.py` has an autouse fixture that sandboxes every test: the user config dir (`config._USER_CONFIG_DIR` and friends) is monkeypatched into a tmp path, the dotenv source is disabled (the repo's own `.env` must not leak), and all `DRCODE_*` variables are stripped — keep this in mind when adding config-layering tests. Common fixtures: `project_root` (fresh tmp dir, the agent's writable root), `manager` (TaskManager over it), `user_config_dir`. The `test_network_*` suite exercises model/network failures (outages, retries, recovery) exclusively through the stubs in `tests/network_mocks.py` — no real API access is needed anywhere.
