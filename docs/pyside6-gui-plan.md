# DrCode GUI (PySide6): план цепочки задач

## Контекст

GUI-приложение DrCode Desktop разрабатывается в **отдельном проекте**, куда
репозиторий drcode подключается **git-субмодулем** — чтобы код оболочки не
засорял основной репозиторий drcode. Все ссылки на код ниже даны относительно
корня субмодуля (`<submodule>/src/drcode/...`, `<submodule>/tests/...`).

Выбранный тулкуит — **PySide6/Qt**: ядро drcode используется in-process
(без IPC/сайдкара), GUI импортирует `drcode.core` как обычную Python-библиотеку
и подписывается на шов событий напрямую.

## Предпосылка — задача 0

Прежде чем начинать цепочку, в drcode должна быть выполнена задача
**#571c19a6** — «Рефакторинг: вынести UI-нейтральную логику из tui/».
Она создаёт шов, без которого GUI строить нельзя:

- пакет `drcode.core/` — pipeline-слои без импорта textual;
- callback-протокол хоста: события `task_updated`, `stream_delta`,
  `service_event`, `notify`;
- UI-нейтральное состояние приложения (реестры ранов/генераций, settings,
  resolved config).

Задача 1 ниже зависит от неё (`depends_on: [#571c19a6]`), каждая
последующая — от предыдущей.

## Правила цепочки

- Каждая задача — **вертикальный срез**: после неё приложение запускается и
  несёт одну логически законченную функцию.
- Каждая задача оставляет: зелёный полный прогон тестов субмодуля
  (`uv run pytest -n 4`), чистые `ruff` + `pyright`, существующий TUI
  **нетронутым**.
- GUI-код живёт в отдельном проекте; в субмодуле drcode допустимы только
  минимальные правки, если шва из #571c19a6 не хватает — и они оформляются
  отдельной задачей в drcode, а не делаются молча.
- Упаковка — строго последней задачей.

---

## Задача 1. Каркас PySide6-приложения

**Зависимости:** #571c19a6.

Каркас отдельного проекта: PySide6-приложение с одним окном, выбором проекта
(нативный диалог папки + список недавних), запуском ядра drcode in-process
(`TaskManager`, settings, resolved config из `drcode.core`).

Шов событий подключается к отладочной консоли/логу внутри окна — все события
(`task_updated`, `stream_delta`, `service_event`, `notify`) видны и
дописываются в файл лога.

**Результат на руках:** запускаемое окно, ядро живёт, конвейер (тестирование
очереди, промоции) работает headless, события observable.

**Критерии приёмки:** параллельный запуск TUI и GUI на одном проекте не
конфликтует (общий `.drcode/`); тест каркаса поднимает ядро на tmp-проекте и
проверяет получение событий.

## Задача 2. Список задач (живая очередь)

**Зависимости:** задача 1.

Экран очереди: таблица/дерево задач (id, kind, статус, verification label,
флаги `unfinished`/`needs_human`/`hold`), обновляемая в реальном времени по
`task_updated`. Данные — из `drcode.core` (task_manager, storage);
паритет полей с сайдбаром TUI (`tui/sidebar_view.py` как образец).

Read-only: без действий над задачами (это задача 5).

**Критерии приёмки:** статусы, промоции, тестирование — отображаются так же,
как в TUI; тест на маппинг событий в модель списка.

## Задача 3. Чат-таймлайн и стриминг

**Зависимости:** задача 2.

Просмотр транскрипта выбранной задачи + live-стриминг активного рана.

Самая технически новая часть — **Rich→Qt рендер**: transcript хранится как
сериализованные `ModelMessage` (`Task.messages`), а TUI рендерит его через
`chat_timeline`/`blocks`. Нужен адаптер Rich-разметки → Qt
(`QTextBrowser`/`QTextDocument`), покрывающий блоки кода, tool-calls,
дельты стрима.

**Критерии приёмки:** история задачи визуально соответствует TUI (порядок,
блоки, код); стрим не роняет интерфейс при ~50 дельтах/сек; тест рендера на
фикстурных транскриптах из `<submodule>/tests/`.

## Задача 4. Ввод пользователя

**Зависимости:** задача 3.

Вводное поле: отправка промпта в задачу (queued input), ответы на уточнения
(`ask_clarifying_question` → возобновление задачи), остановка рана (эквивалент
ESC/Ctrl+R по семантике `tui/actions.py`).

После этой задачи GUI — рабочий инструмент: задачу можно вести от создания до
комплита не выходя из GUI.

**Критерии приёмки:** ввод уходит через ядро с той же семантикой
(`pending_input`, auto-resume `unfinished`); уточнение ставит задачу в
awaiting-clarification и отвечает из GUI; тесты на оба пути.

## Задача 5. Управление задачами

**Зависимости:** задача 4.

Создание задач (bug/feature/research), hold/unhold, cancel, delete (только
held), редактирование зависимостей (с `validate_dependencies`-гейтом),
перестановка в очереди. Образцы семантики — `task_manager.py`
(`set_hold`, `cancel`, `move_in_queue`, `set_dependencies`) и
`tui/actions_lifecycle.py`.

**Критерии приёмки:** каждая операция имеет точный паритет с TUI-поведением
(в т.ч. запреты: delete только для held, dep-gate на промоции); тесты по
списку операций.

## Задача 6. Настройки и модели

**Зависимости:** задача 5.

Экраны настроек: выбор моделей по ролям из пользовательского каталога
(`providers.resolve`/`resolve_effective`, каталог `~/.config/drcode/`),
project-level выбор (`models[role]` ref/custom), project settings
(изоляция, параллельность, ретеншн и пр.). Образцы — `providers.py`,
`settings.py`, `tui/task_settings_dialog.py`.

**Критерии приёмки:** изменения пишутся в те же конфиг-файлы, что пишет TUI
(взаимозаменяемость GUI↔TUI на одном проекте); тесты на чтение/запись слоёв.

## Задача 7. Паритетные индикаторы

**Зависимости:** задача 6.

Второстепенные виджеты паритета с TUI: todo-панель чек-листа, сервис-события
в чате, activity-индикатор (fresh/stale, stall countdown), usage/статистика,
уведомления. Образцы — `tui/todo_panel.py`, `tui/activity_view.py`,
`tui/usage_dialog.py`, `tui/stats_dialog.py`.

**Критерии приёмки:** все источники данных — `drcode.core`/`usage_store`
без обращений к `tui/`; чек-лист паритета заполнен, отсутствующее явно
помечено.

## Задача 8. Упаковка и CI

**Зависимости:** задача 7.

Сборка дистрибутивов отдельного проекта: payload — PyInstaller-оболочка GUI +
субмодуль drcode.

- **macOS**: `.app` (Info.plist, иконка), подпись + нотаризация
  (Apple Developer ID; локально ad-hoc + ПКМ→Open).
- **Linux**: AppImage + `.deb`.
- **CI**: джобы сборки на macos-14 и ubuntu; артефакты к релизу по тегу `v*`
  нового проекта. Версия GUI = версия субмодуля drcode.

**Критерии приёмки:** свежесобранные артефакты запускаются на чистой машине
(без dev-окружения): macOS arm64 и Linux x86_64; ручной чек-лист из задач
1–7 проходит в запакованном приложении.

## Задача 9. Merge-экран (человеческий конфликтный UI)

**Зависимости:** задачи 1–7 (осознанно вынесен за первый релиз — самый
сложный экран TUI, `tui/merge_screen.py` ~2200 строк).

Порт функциональности человеческого разбора конфликтов:

- разбор zdiff3-хунков на решения `ours`/`theirs`/`both` (паровоз на
  `drcode/conflict.py` — LLM-free парсер, переиспользуется напрямую);
- отображение триаж-отчёта из `.drcode/merge_reports/<task-id>.json`
  (`merge_engine.py`: kind'ы конфликтов, применённые авто-резолверы);
- стейджинг файла только когда маркеров не осталось; `finish`/`abort` через
  `merge_engine.finish`/`abort`;
- экран незмердженных веток (образец `tui/unmerged_screen.py`);
- для parked-конфликтов (`task.needs_human`) — вход в экран из списка задач.

LLM-слой (`merge_resolver.py`) НЕ портируется — он остаётся в ядре и
запускается так же, как в TUI; GUI только показывает его вердикты и
верификационную воронку (`mechanical_checks`, `run_test_suite`,
`review_diffs`).

**Критерии приёмки:** parked-конфликт можно полностью разобрать руками в GUI
(решения по хункам, стейджинг, finish/abort); контракт «drcode никогда не
мержит в пользовательский checkout» не нарушен; тесты на парсинг и
finish/abort через GUI-модель.
