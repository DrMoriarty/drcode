# compaction-bench

Автономный бенчмарк качества моделей-компактизаторов (context-summarization
для кодинг-агентов) на реальных транскриптах. Папка самодостаточна:

- **ноль импортов из drcode** — бенчмарк читает только снимки датасета и
  промптов, лежащие рядом;
- **ноль сторонних pip-зависимостей** — только стандартная библиотека Python
  3.10+;
- переносится в отдельный репозиторий как есть.

Мотивация: компактизатор — узкое место качества длинных кодинг-сессий. Потеря
пути файла или решения в сводке напрямую ломает продолжение работы, а
деградация формата (например, ответ JSON-конвертом вместо markdown) ломает
парсинг у потребителя. Бенчмарк измеряет это на настоящих транскриптах, а не
на синтетике.

## Структура каталога

```
compaction-bench/
  README.md           # этот документ
  bench/
    __init__.py
    extract.py        # сборка датасета из .drcode/tasks разных проектов (будущая задача)
    run.py            # раннер + детерминированные метрики (Tier A) + агрегаты (будущая задача)
    qa.py             # Tier B: генерация вопросов, ответы, судья (--qa) (будущая задача)
  prompts/            # снимок compaction.txt / compaction.md (см. prompts/README.md)
    README.md         # провенанс: откуда и когда сняты промпты
    compaction.txt    # system prompt компактзора
    compaction.md     # шаблон выходной структуры сводки
  dataset/            # manifest.json + cases/<project>-<taskid>.json
  results/<run-id>/   # конфиг прогона, per-case JSON, агрегат CSV + Markdown
```

`dataset/` и `results/` пустые в репозитории (`.gitkeep`); датасет собирается
`bench/extract.py`, результаты появляются от прогонов `bench/run.py`.

## Формат кейса датасета (вариант A)

Кейс — **самодостаточный JSON-файл** (`dataset/cases/<project>-<taskid>.json`),
не требующий доступа к исходным транскриптам во время прогона. Рендер истории
фиксируется на момент экстракции; раннер ничего не перерендеривает.

```jsonc
{
  "case_id": "drcode-1234abcd",              // "<project>-<task_id>"
  "source": { "project": "drcode", "task_id": "1234abcd" },
  "task": { "title": "...", "kind": "feature", "lang": "ru" },
  "original_prompts": "...",                  // дословные пользовательские промпты задачи
  "history_blocks": [                         // история диалога в порядке следования
    { "kind": "user",        "text": "..." },
    { "kind": "assistant",   "text": "..." },
    { "kind": "tool-call",   "text": "..." },
    { "kind": "tool-result", "text": "..." }   // обрезан до 20k символов (как в проде)
  ],
  "previous_summary": "...",                  // anchored-сводка прошлой компактизации или null
  "checklist": "...",                         // todo-чеклист задачи или null
  "stats": {
    "history_chars": 0,                       // сумма длин history_blocks
    "est_tokens": 0,                          // chars/4, без токенизатора
    "n_blocks": 0
  }
}
```

`manifest.json` в корне `dataset/`: sha256 каждого кейса, список источников
(проекты, количество кейсов), дата сборки, применённые фильтры.

### Фильтры экстракции

- статус задачи — `completed`;
- транскрипт непустой;
- `est_tokens` в диапазоне 20k–600k;
- не более одного кейса на задачу;
- tool-result-блоки обрезаны до 20 000 символов (та же капа, что в проде).

### Сплит и источники

Dev/test сплит фиксируется при сборке (детерминированный, по хешу `case_id`)
и замораживается в manifest — метрики на dev и test не смешиваются.

Ожидаемые источники (~945 транскриптов): drcode (~807), grid-apps (94),
drcode-desktop (21), bibisco-ng (20), apex-quant (5), finbot (2). У ~106
кейсов есть `previous_summary` — это кейсы **повторной компактизации**,
учитываются отдельным срезом в агрегатах.

## Композитный скор 0–100

Каждый компонент отчётный отдельно; композит — взвешенная сумма. Веса —
конфиг прогона (см. ниже), значения по умолчанию:

| Компонент | Вес | Тип | Что измеряет |
|---|---|---|---|
| Формат-комплаенс | 10 | детерминированный | секции шаблона присутствуют и идут по порядку; нет JSON-обёртки и code fences; вывод начинается с заголовка; чеклист перенесён |
| Язык | 5 | детерминированный | эвристика кириллица/латиница: язык сводки против языка диалога (`task.lang`) |
| Recall идентификаторов | 25 | детерминированный | пути файлов + идентификаторы, извлечённые из полной истории → доля вошедших в сводку; штраф за галлюцинированные (не встречавшиеся в истории) пути |
| Сжатие | 10 | детерминированный | токены сводки / токены истории; целевая полоса ~5–15%, жёсткий провал (0) за пределами |
| QA-точность | 30 | Tier B (LLM) | экзаменатор генерирует N фактических вопросов + золотые ответы из полной истории; отвечающая модель видит **только** `original_prompts` + сводку + чеклист; судья сравнивает ответы с золотыми |
| Судья-рубрика | 20 | Tier B (LLM) | LLM-судья (temperature 0, модель фиксируется в отчёте) со ссылкой на полную историю: полнота Done / In-Progress / Next / Decisions, отсутствие галлюцинаций |

### Тиры

- **Tier A = 50 баллов** (первые четыре компонента) — детерминированные,
  бесплатные, без LLM-судьи. Режим по умолчанию.
- **Tier B = полные 100 баллов** — добавляет QA-точность и судью-рубрику,
  включается флагом `--qa` (задействует `bench/qa.py`).

Краш-кейсы (таймаут модели, невалидный формат, HTTP-ошибка) получают 0 по
всем содержательным компонентам и попадают в счётчик `failures` агрегата —
выбросить кейс тихо нельзя.

## Процедура прогона и воспроизводимость

- **temperature=0** для всех вызовов (компактизатор, экзаменатор, судья).
- Промпты зафиксированы снимком в `prompts/`; прогоны ссылаются на коммит
  снимка.
- **hash датасета** (sha256 из manifest) печатается в отчёте прогона.
- Модели судьи и экзаменатора **фиксируются и указываются** в отчёте.
- Per-case JSON пишутся в `results/<run-id>/` **по мере готовности** —
  рестарт докатывает незавершённые кейсы, готовые не пересчитывает.
- Ключевые модели прогоняются **×2** для оценки недетерминизма (два run-id,
  разброс метрик попадает в агрегат).

`results/<run-id>/` содержит: `config.json` (все параметры прогона, веса
компонентов, модели, base-url, дата), per-case JSON, агрегат `summary.csv` +
`summary.md`.

## Интерфейс раннера

OpenAI-совместимый `/v1/chat/completions` через `urllib` — локальные
Ollama / LM Studio / vLLM и удалённые API ходят одним механизмом. Токены
оцениваются как `chars/4`, без токенизатора.

```
python bench/run.py \
  --base-url http://localhost:11434/v1 \
  --model qwen3:32b \
  [--api-key KEY]        # или env OPENAI_API_KEY / DRCODE_BENCH_API_KEY; иначе без ключа
  [--workers N]          # ThreadPoolExecutor; 1 = без параллельности (по умолчанию 1)
  [--mode single|mapreduce|auto]
                         # single   — вся история одним запросом
                         # mapreduce — срезы истории с фиксированным бюджетом,
                         #            reduce-промпт как в проде
                         # auto     — single до лимита контекста, затем mapreduce
  [--qa]                 # включить Tier B (qa.py): QA-точность + судья-рубрика
  [--dataset DIR]        # default: ../dataset относительно bench/
  [--out DIR]            # default: results/<utc-timestamp>-<model>
  [--weights JSON]       # переопределение весов компонентов композита
  [--limit N] [--split dev|test] [--cases id1,id2]
```

Минимальный прогон Tier A на локальной модели:

```
python bench/run.py --base-url http://localhost:11434/v1 --model qwen3:32b
```
