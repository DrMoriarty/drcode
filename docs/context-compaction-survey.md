# Компактизация контекста: обзор современных методов и оценка имплементируемости в drcode

> Исследование по цели `acd3c0c8` («Исследование современных методов компактизации
> контекста в AI-агентах»). Дата: по состоянию на конец 2025 / начало 2026.
> Источники — официальная документация и репозитории инструментов; непроверенные
> утверждения помечены явно.

## TL;DR

Самое прогрессивное на текущий момент — не один алгоритм, а **эшелонированная
система**: (1) дешёвая селективная выгрузка старых tool-результатов до всякой
суммаризации, (2) суммаризация по порогу с сохранением якорей, (3) **фоновая
(превентивная) компактизация**, которая готовит суммари заранее и не блокирует
ход агента — экспериментальная фича OpenCode v2, (4) внешняя файловая память,
переживающая сброс контекста. drcode уже имеет прочный фундамент (порог 80%,
якорная цепочка суммари, map/reduce, механический пол, eviction по меткам,
pre-run idle-компактизация); до лидеров не хватает в первую очередь
**автоматической очистки tool-результатов** и **фоновой компактизации** — оба
метода ложатся на существующую архитектуру без её ломки.

## 1. Текущее состояние drcode (отправная точка)

Что уже реализовано, с привязкой к коду:

| Механизм | Где | Суть |
|---|---|---|
| Пороговая компактизация | `config.py` (`compaction_threshold = 80`), `core/pipeline_compaction.py:_fill_over_threshold` | При заполнении 80% окна (per-role/per-model, переопределяется в каталоге моделей) ход ставится на паузу, транскрипт суммаризируется |
| Якорная цепочка суммари | `compaction.py` (`COMPACTION_SUMMARY_PREFIX`, `extract_previous_summary`) | Суммари цепляется за предыдущее; оригинальные пользовательские промпты сохраняются вербатим всегда |
| Map/reduce для длинных транскриптов | `compaction.py` (`_MAX_REDUCE_DEPTH = 3`) | История нарезается на слайсы по бюджету окна суммаризатора, партиалы сливаются иерархически |
| Механический пол (LLM-free) | `compaction.py:mechanical_compaction_messages` | Когда суммаризатор физически не влезает в окно — обрезка по границам сообщений без LLM |
| Селективная выгрузка по меткам агента | `eviction.py`, `core/pipeline_compaction.py:_maybe_evict_marked` | Агент помечает ненужное через `mark_unneeded`; на 1/3 окна всё помеченное сворачивается в заглушки одним батчем (одна инвалидация промпт-кэша) |
| Pre-run idle-компактизация | `core/pipeline_compaction.py:_maybe_compact_after_idle` | При простое ≥180 c и заполнении ≥ `compaction_resume_min_tokens` (мин. 20 000) транскрипт ужмается ДО запуска следующего раунда — кэш всё равно холодный |
| Housekeeping при смене модели | `_prepare_model_switch_transcript` | Срыв thinking-частей чужой модели, форс-компактизация ≥20k токенов, takeover-заметка |
| Оценка заполнения | `context_layout.py`, `transcript.py` | `len/4` без токенизатора, точные usage-цифры API учитываются отдельно |
| Изоляция контекста субагентами | `subagents.py` (`delegate_research`) | Широкое чтение — в чистом окне субагента, родителю возвращается только выжимка |

Уже покрыто из «передового»: якорная суммаризация (≈ Claude Code), map/reduce,
механический пол, ручная eviction (≈ tool result clearing, но по инициативе
агента), субагенты (≈ Anthropic sub-agent architecture), pre-run компактизация
(частичный аналог фоновой).

## 2. Что есть у других инструментов

### 2.1 OpenCode v2 — фоновая компактизация (главный запрос)

Источник: PR [anomalyco/opencode#58294](https://github.com/anomalyco/opencode/pull/58294)
(переименование флага, там же новая документация), changelog v2.2.7, issue
[#60410](https://github.com/anomalyco/opencode/issues/60410).

Как устроено:

- **Флаг конфига**, экспериментальный: `{ "experimental": { "background_compaction": true } }`
  в `opencode.json`. Переименован из `precompute_compaction` прямо перед релизом:
  «`precompute_compaction` described the mechanism. `background_compaction` is
  what people will look for».
- **Суть — precompute**: суммари готовится ЗАРАНЕЕ, в фоне, параллельно с идущей
  работой агента, а не в момент переполнения. Обычная компактизация OpenCode
  (`/compact`, авто-режим `compaction: { "auto": true }`, «kicks in around turn
  completion») срабатывает на границе шага и стоит перед ожидающими промптами;
  фоновая устраняет этот блокирующий такт.
- Задокументированные свойства (таблица из PR #58294): у фоновой суммаризации
  есть **стоимость** (отдельный запрос к модели); при некоторых условиях она
  **откатывается к обычной суммаризации**, при некоторых **пропускается**;
  удержанные (held) суммари **теряются при рестарте**.
- Реализовано как плагин сессии в ядре: чтение флага —
  `packages/core/src/config/plugin/compaction.ts`.
- Эволюция качества: в v2.2.7 багфикс «a background summary no longer stops a
  running Claude Agent session mid tool call» — то есть фон ещё недавно умел
  прерывать живой tool call; фича молодая и сырая.

Чего в источниках нет: точный триггер запуска (порог/процент окна) и состав
сохраняемого — исходники `compaction.ts` и ранние PR (#57444) не были
просмотрены.

### 2.2 Claude Code / Anthropic

Источники: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [Context management](https://claude.com/resources/articles/context-management), [Claude Code costs](https://code.claude.com/docs/en/costs).

1. **Компакция суммаризацией** — история передаётся модели на сжатие:
   сохраняются архитектурные решения, незакрытые баги, детали реализации,
   выбрасываются избыточные tool-выводы; агент продолжает со сжатым контекстом
   **плюс пятью последними открывавшимися файлами**. Рекомендация по промпту
   суммаризатора: сначала максимизировать recall («захватить всё релевантное»),
   затем повышать precision (вычищать лишнее). Это практически наш текущий
   подход — совпадение подтверждает, что фундамент у нас правильный.
2. **Tool result clearing («микрокомпакция»)** — «safest lightest touch form of
   compaction»: старые tool-вызовы и результаты удаляются из истории, поток
   разговора сохраняется. В Claude Code это отдельный путь наряду с полной
   компакцией (виден в статистике промпт-кэша как «expected rebuild»).
   Ключевое отличие от нашего `eviction.py`: у Anthropic очистка **автоматическая**,
   у нас — по меткам самого агента (`mark_unneeded`).
3. **Context editing API** (платформа, public beta, Sonnet 4.5) — то же самое,
   но как сервисная функция API: «automatically clears stale tool calls and
   results from within the context window when approaching token limits».
   Замеры Anthropic: context editing отдельно — +29% к качеству agentic search,
   вместе с memory tool — +39%; в 100-ходовом web-search eval — «reducing token
   consumption by 84%». Vendor-specific API, напрямую не переносим — но идея
   совпадает с п. 2.
4. **Memory tool** — файловая память вне окна: модель через CRUD-инструменты
   читает/пишет файлы в выделенной директории, персистентной между сессиями;
   работает целиком клиентски. Идея «structured note-taking»: NOTES.md/todo как
   память, которую читают после сброса контекста.
5. **Sub-agent архитектуры** — субагент тратит десятки тысяч токенов на
   исследование и возвращает родителю 1–2k токенов выжимки. Выбор механизма по
   сценарию: compaction — длинный диалог, note-taking — итеративная разработка,
   multi-agent — параллельное исследование.
6. **Just-in-time retrieval** — вместо предзагрузки агент держит лёгкие
   идентификаторы (пути, grep) и подтягивает данные по требованию.

Фоновая/асинхронная компакция у Anthropic в изученных источниках не
описана — их context editing синхронный («when approaching token limits»).

### 2.3 Прочие инструменты

- **Gemini CLI** (проверено по README [репозитория](https://github.com/google-gemini/gemini-cli)):
  token caching на стороне API, checkpointing сессий, иерархическая память
  GEMINI.md (глобальный → проектный → подпапки). Slash-команда `/compress`
  (замена истории суммари, старая часть суммаризируется, свежая — вербатим) и
  авторежим с порогом `compressionThreshold` — **по памяти, фетчем не проверено**.
- **Aider** — **по памяти, фетчем не проверено** (сайт aider.chat требует JS):
  repository map (tree-sitter парсит репо, граф ссылок, PageRank-подобное
  ранжирование символов, карта сигнатур занимает ~25% окна, `map-multiplier`
  настраивается) и суммаризация старой половины истории при переполнении.
- **Cline** — **по памяти, не проверено** (docs.cline.bot не отдал контент):
  context condensing — автосуммаризация старых сообщений по sliding-window при
  приближении к лимиту, транкейция крупных tool-outputs, Focus Chain/todo как
  персистентная память между компакциями.
- **OpenAI Codex CLI** — проверить не удалось: developers.openai.com отдаёт 403,
  docs в репо — заглушка со ссылкой на тот же сайт.

## 3. Оценка имплементируемости в drcode

| Метод | Сложность | Куда встраивается | Комментарий |
|---|---|---|---|
| **Автоочистка старых tool-результатов** (Claude Code tool result clearing) | **Низкая** | `eviction.py` + `_maybe_evict_marked` — вся инфраструктура заглушек, сохранения call/return пар и батчинга уже есть | Добавить автоматический критерий поверх agent-меток: tool-результаты старше N ходов (кроме якорных — последние K) сворачиваются в stub на том же гейте 1/3 окна. Главное решение — какие результаты считать «свежими» (последний доступ к файлу, вывод тестов). Это самый дешёвый способ получить замеренные Anthropic +29%/84% эффекты |
| **Фоновая компактизация** (OpenCode v2) | **Средняя** | `_maybe_compact` (сейчас: пауза → суммаризация → резюм) плюс воркер-слот, не занимающий dev-слот | Два принципиальных момента: (1) гонки — фоновый суммаризатор читает транскрипт, пока агент его пишет; нужна защита генерацией в духе `_agent_runs` и точка согласованности (коммит суммари только на границе хода); (2) экономика — преждевременная компактизация убивает промпт-кэш, поэтому фоновый запуск имеет смысл только когда заполнение уже близко к порогу и продолжается рост. Опыт OpenCode (фоллбек на обычную компактизацию, пропуск условий) подтверждает: нужны оба пути параллельно. Наш `_maybe_compact_after_idle` — уже частный случай (фоновая компактизация «между» раундами); полноценная фоновая во время раунда — следующий шаг |
| **Memory tool / файловая память** | **Средняя** | Новый инструмент в `agent_tools.py` + директория в `task_env` scratch | У нас частично есть (todo-чеклист живёт в `task.todos` вне транскрипта и подмешивается в суммари; task-facts); полноценная персистентная память между сессиями — скорее feature, чем компактизация |
| **Точный подсчёт токенов** вместо `len/4` | **Средняя** | `context_layout.py`, `transcript.py` | Все гейты сидят на эвристике с запасными полями (`_SLICE_SAFETY_MARGIN`, `_MECHANICAL_MARGIN_PCT`); API usage-цифры уже приходят с живыми ходами (`_live_ctx_tokens`) — можно расширить их использование на pre-run гейты. Снижает и перерасход (лишние компактизации), и недобор (overflow) |
| **Repository map** (Aider) | **Средне-высокая** | Новый модуль + tree-sitter-зависимость | Ортогонально компактизации: это выборочная подача кода (JIT retrieval), а не сжатие истории. Большая самостоятельная работа |
| **Context editing API** | неприменимо | — | Vendor-специфичный endpoint Anthropic; идея уже покрыта строкой «автоочистка tool-результатов» |

## 4. Рекомендуемый порядок

1. **Автоочистка старых tool-результатов** — минимальный дифф поверх
   существующего eviction-конвейера, максимальное отношение эффекта к риску.
2. **Фоновая компактизация** — начать с расширения существующего
   `_maybe_compact_after_idle` (превентивный запуск при приближении к порогу ещё
   ДО простоя, на границе ходов), затем — параллельный фоновый суммаризатор с
   коммитом на границе хода, как в OpenCode v2.
3. **Точный токен-каунтинг** — сквозное улучшение точности всех гейтов.
