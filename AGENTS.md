# AGENTS.md

## Commands

```bash
uv sync                  # install deps into .venv (Python 3.12, src layout)
uv run drcode            # run the TUI — operates on the CURRENT directory (Path.cwd())
uv run ruff check src    # lint (no config; ruff defaults)
uv run ruff format src
uv run pyright           # typecheck (dev dep; no config)
```

No tests, CI, or pre-commit hooks exist — verify changes manually with ruff + pyright, and exercise the TUI by launching `uv run drcode` in a scratch directory.

## Configuration gotcha

The agent needs `model` and `base_url`; `api_key` is optional (keyless local gateways work — an empty key omits the Authorization header / sends a placeholder). Settings are layered (higher wins): `DRCODE_*` env vars > project `.env` / project `.drcode/drcode.json` > user-level `~/.config/drcode/drcode.json` (XDG_CONFIG_HOME-aware) > built-in defaults (see `src/drcode/config.py`). On first start the user config dir is scaffolded with `drcode.json.example` listing every configurable parameter — when adding a new `Config` field, add a placeholder to `_EXAMPLE_PLACEHOLDERS` if it has no sensible default. When nothing anywhere provides model/base_url, the TUI opens a modal setup dialog on startup (`tui/setup_dialog.py`): model and URL are required, API key and max context tokens optional; ESC skips (the app runs without a model — tasks can be created and browsed, the pipeline stays idle), Save probes the endpoint live and on success persists the values into `<project>/.drcode/drcode.json` (`Config.save_to_project`, merged with existing keys) and starts the pipeline. `base_url` defaults to the OpenAI API; any OpenAI-compatible endpoint works.

## Architecture

Task-centric coding agent (pydantic-ai + textual), inspired by opencode. Single package under `src/drcode/`:

- `task_manager.py` — state machine: queued → active → testing → completed, plus awaiting-clarification: the agent's `ask_clarifying_question` tool pauses the task on a question and the pipeline advances; when the user answers, the task re-enters the pipeline at the head of the queue (activated once no testing is pending and nothing is active — promotion is up to the app, see `tui/app.py`). At most one ACTIVE task; when it's marked done (development finished) it moves to TESTING — only the tester moves it to COMPLETED via `set_verification` (which also stamps the passed/failed label). A task also auto-completes (goes to TESTING) when the agent finishes its run with no pending input, no clarification and no unfinished attempt; aborts and agent errors keep the task paused via `task.unfinished` instead. Sending input to a COMPLETED/TESTING task re-queues it (the old verification label is cleared). On startup any stale ACTIVE task is demoted to queued, and all tasks stuck in TESTING are re-tested FIRST, before any queued task is taken into development (awaiting-clarification tasks survive restarts). `promote_next` activates a queued task that has pending input OR an unfinished attempt (auto-resume of interrupted work) — never a held one: the user can park a queued task out of the backlog (`TaskManager.set_hold`, Ctrl+H in the TUI); a held task keeps its pending input and queue stamp but is skipped by queued() until explicitly resumed (Ctrl+H again) — or fully deleted (`TaskManager.delete`, Ctrl+Delete in the TUI, removes the task from memory and disk; only held tasks can be deleted). `cancel` (user: Ctrl+X) drops all pending input and completes the task immediately — the tester is skipped everywhere a finished task would run it. `research` tasks never go to TESTING: `mark_done` completes them right away (the tester is skipped everywhere a finished task would run it). The kind of a still-queued task can be changed (`TaskManager.set_kind`, Ctrl+T in the TUI): bug re-positions it at the head of the queue, feature — at the tail; other kinds keep the position. The user can also reorder the backlog manually (`TaskManager.move_in_queue`, Ctrl+Up / Ctrl+Down in the TUI): one step up = away from execution, one step down = closer to it; the order is re-stamped into `queue_seq` so it survives restarts, later tasks still enter by the default algorithms, and moves never cross the bug block (bugs always run first). Queue order is `(bugs newest-first, queue_head, queue_seq)` where `queue_seq` is a monotonic stamp (creation order by default, bumped on re-positioning).
- `models.py` — `Task` holds the full pydantic-ai transcript as serialized `ModelMessage` dicts (`task.messages`); queued user input lives in `task.pending_input` until the agent run consumes it. `task.unfinished` marks an interrupted attempt (abort/agent error): the consumed prompt is NEVER re-queued — it stays in the transcript at its chronological position, and the next activation resumes the attempt without re-sending text. Tester runs are persisted separately in `task.tester_messages` (one serialized transcript per testing round) so they never leak into the coding agent's model history; the chat renders each round behind a "testing" separator. `task.events` (`TaskEvent`: timestamp + text) is the service-event log (tester/agent failures, skips) — shown in the chat under a "service events" separator, but never fed to the model, since it lives outside both transcripts.
- `storage.py` — persists each task as `<project>/.drcode/tasks/<id>.json` (atomic tmp-file write; corrupted files are moved to `.json.bak`, not deleted). `.drcode/` is gitignored.
- `agent.py` — builds the pydantic-ai `Agent` with tools registered inline; `deps` is just the project root (`Path`). `serialize_messages`/`load_messages` round-trip transcripts; `resumable_history` trims an incomplete tail (unanswered tool calls / bare tool results) before a transcript is resumed; `sanitized_messages` applies the same trim at interrupt time so the stored transcript stays API-valid no matter in which order later messages are appended; `ends_with_open_request` tells whether a continuation turn has something to resume; `extract_display` renders them for the chat UI.
- `tools.py` — filesystem/shell tools for the agent. Reading (`read_file`) works anywhere on the filesystem; writing (`write_file`/`edit_file`) is jailed to the project root and `/tmp` (symlink-aware, so `/private/tmp` on macOS counts too) — violations raise `PathViolation` with a model-friendly message. `run_bash` inspects the command first and refuses `rm`/`mv`/`cp` whose path arguments escape the writable area. The agent layer (`agent.py`) logs every `PathViolation` into the task's service-event history and converts it into a retry prompt. Grep/glob skip `IGNORED_DIRS` (add new cache dirs there).
- `tui/app.py` — textual app. `run_agent` is a `@work(exclusive=True, group="agent")` worker whose loop processes messages strictly chronologically: pending input in arrival order, then at most one continuation turn (`agent.iter(None, …)`) when `task.unfinished` and the transcript ends with an unanswered request; the interrupted prompt is never re-queued, and both the cancel and error handlers sanitize the transcript instead of re-queueing text. Agent errors push the failed attempt to `unfinished` + demote the task to QUEUED so nothing is lost. Pipeline advancement goes through the single `_advance()` gate: while any task is TESTING, no new development ever starts — the oldest TESTING task is (re)tested first, and a failed tester run is retried with capped exponential backoff (the pipeline waits; the retry timer re-advances). Cancelled workers (abort, superseded runs) do not restart the pipeline. Ctrl+X cancels the viewed task (`manager.cancel`): pending input dropped, completed immediately, no testing. Service events are persisted via `_log_event`/`_show_event` regardless of which task is open in the chat.
